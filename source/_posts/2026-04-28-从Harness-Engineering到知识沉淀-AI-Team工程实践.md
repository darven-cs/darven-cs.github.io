2026 年最火的 AI 工程话题是什么？毫无疑问是 Harness Engineering。

各种解读铺天盖地——有人研究该用多大的模型，有人研究该搭多复杂的工作流，有人研究 Agent 怎么协同。但我和团队在深度落地实践后，发现了一个被普遍低估的事实：**工作流只是管道，知识才是流过管道的活水。**

## 热潮中的冷思考

先说个有趣的观察。

OpenAI 的 Codex 强调人机交互协议，Cursor 的 Self-Driving 强调多 Agent 协同，Anthropic 的 Claude Code 强调长时运行的稳定性。这些实践都很兴奋，但它们都有一个共同点——都在讲**工具链怎么设计**。

几乎没人讨论：**工具链里的"知识"从哪来？**

这让我想起圆桌讨论里的一个论断："将来的技术护城河不在模型，而在垂直领域知识的沉淀。"模型会迭代，工具链会更新，工作流会重构。但"广告扣减在高并发下会超扣，需用 Redis+Lua 保证原子性"这条知识，不管你用什么模型、什么工作流，它都有价值。

**知识是可累积的，工作流是可替换的。** 这个判断，是我一年实践下来最核心的体会。

## 工作流跑不通的真正原因

很多团队搭了很复杂的 Agent 工作流，16 阶段状态机看起来很美。但每次需求来了，跑一遍全流程；下次需求来了，再跑一遍。上一次踩过的坑，下一次照踩不误。上一次做过的架构决策，下一次重新推导一遍。

这不是工作流的问题，这是**没有知识闭环**的问题。

投入了大量工程成本搭建工具链，却没有让工具链变得越来越聪明。每次都是"一次性"的使用。

## 知识的三种形态

不是所有知识都等价。我在实践中把知识分成三类：

**散点型知识**是最浅的形态——孤立的事实，比如"我们用的数据库是 TencentDB for MySQL 8.0"。这类知识容易获取，但也容易过时。

**因果型知识**更有价值——"A 导致 B"的推理链。比如"为什么选择事件驱动而非 RPC 同步，因为广告状态变更需要解耦"。这类知识需要推导和验证，是团队真正的经验沉淀。

**时空型知识**最难获取——它是特定场景和时间窗口下才成立的经验。比如"这个接口在双十一流量峰值下会超时，需要加本地缓存"。这类知识几乎不可能从模型直接获得，只能靠团队在实战中积累。

越高级的知识，越依赖实践积累。模型可以给你散点型知识，但给不了你时空型知识。

## 五层知识架构：让知识有序沉淀

实践下来，知识必须有分层的设计。我们分了五层：

**Layer 0-P（个人偏好）**是纯个人的——你喜欢 4 空格还是 2 空格缩进？这是你自己的，不应该强制给团队。

**Layer 0-T（团队约定）**是团队的"宪法"——代码规范、Commit 规范、Review 标准。相对稳定，所有人共同遵守。

**Layer 1（技术知识）**是跨项目通用的技术经验。比如"Spring Boot 多租户拦截器设计模式"、"Optional 依赖传递陷阱"。这类知识可以在多个项目间复用。

**Layer 2（业务知识）**是特定领域的——领域模型、业务规则、审核流程。比如"广告审核：提交→机审→人审→上线"。

**Layer 3（项目知识）**是只在当前项目有意义的上下文。项目结束了，这层知识也随之归档或提升到更上层。

一个关键设计：**知识可以向上提升**。Layer 3 的项目知识如果被判定为跨项目通用，自动提升到 Layer 1 或 Layer 2。这样知识不会被单个项目的生命周期绑架。

## 知识也有生命周期

知识不是写完就完了，它会过时。

我们设计了三极成熟度：**draft**（单一来源）→ **verified**（单项目验证）→ **proven**（多项目验证）。但更重要的是**自动衰减机制**：

proven 条目 12 个月没人引用，降级；verified 6 个月没人引用，再降；持续没引用的 draft 条目，直接归档移出活跃索引。

为什么需要衰减？因为知识也会过期。三年前的"最佳实践"，可能因为框架版本升级已经不再适用。与其让过时知识误导 Agent，不如让它自然退出活跃库。

## 工作流是知识的载体，不是终点

怎么让知识真的沉淀下来，而不是停留在"写文档"的层面？

我们的做法是让工作流成为知识的**进出口**。

**进口**：工作流启动时（INIT 阶段），自动 git pull 团队知识仓库，把知识全景注入 Agent 的查询入口。新启动的工作流自动站在前人肩上，不需要从零开始。

**出口**：工作流完成后（ARCHIVE 阶段），自动从全流程产物中提取知识——架构决策提炼成 decision，踩过的坑提炼成 pitfall，总结的经验提炼成 guideline。然后执行提升判定，符合条件的自动升到 Layer 1 或 Layer 2。

这样，每跑一次工作流，知识库就变聪明一点。这才是 Harness Engineering 真正有价值的地方。

## 知识的消费方式：按需查询，而非一股脑推送

传统的做法是在 Agent 启动时，把一堆知识"推送"给它。结果要么是信息过载（Agent 被淹没在大量知识里找不到关键信息），要么是不精准（预先推送的知识不是当前决策点真正需要的）。

我们设计的是**三级渐进式索引**：

- 先读全景目录（~50 行），了解知识库有什么分类
- 再读分类清单（~100-300 行），按标签过滤出相关条目
- 最后才按需读完整条目（每条 50-200 行）

用 ~50 行的成本了解全貌，用 ~300 行的成本定位到相关条目，只在真正需要时才读完整内容。这比一次性推送 50 条完整知识（可能 5000-10000 行）效率高一个数量级，同时避免了上下文膨胀的问题。

## 最后

这篇文章不是讲怎么搭 Harness 工作流，那是显学的部分。

我想强调的是：**工具链是表，知识沉淀是里**。当你花了三个月搭好一套 Agent 工作流，感觉很成就的时候，问自己一个问题——这套工作流跑完之后，团队留下了什么？

如果答案只是跑出了产物，那这套工作流的价值是有限的。如果答案是知识库多了一批 proven 知识，那才说明你真正建立了技术护城河。

模型会越来越强，工具会越来越多。但一个团队在特定业务领域积累的领域知识、架构决策、最佳实践——这些东西，是真正不会因为模型换代而失效的资产。

**把工作流变成知识的进出口，比把工作流搭得好看更重要。**
